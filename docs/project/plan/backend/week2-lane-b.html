What shipped

Eight contracts, each with a named test class and a file you can open. The execution record in the week-2 plan (§11) carries the full review history; this is the operator’s view.

  1. 01

    E.164, Argon2id and the admin seed

    One shared normalizer: a leading + or 00, spaces and dashes are accepted, the result is +<digits> for 8–15 ASCII digits and null otherwise. Passwords hash with Argon2id over the shared core/backend primitive. The bootstrap admin is upserted from HOPA_ADMIN_EMAIL/HOPA_ADMIN_PASSWORD at boot, with a lowercased email.

    Where core/backend/.../accounts/Phones.kt, accounts/Passwords.kt, accounts/AdminSeed.kt Proof AccountsUtilTest

  2. 02

    Sign-up and sign-in

    POST /v1/accounts creates the account, a household-of-one, the owner member, the first device, its self-wrap and the token pair in one transaction. POST /v1/session signs in an existing account and mints a signed-in device. An unknown phone and a wrong password answer the same E_AUTH, rate limits are per IP and per phone, and a duplicate sign-up race maps SQLState 23505 to the same E_AUTH.

    Where accounts/AccountService.kt, accounts/AccountRoutes.kt Proof AccountRoutesTest

  3. 03

    Optional SMS OTP

    POST /v1/session/otp and /verify sit behind HOPA_SMS_ENABLED (default false), wired to a log-only SmsPort. A verified login takes over an unverified account; an unknown phone creates a verified household-of-one with a throwaway password hash and no wrap. No vendor contract ships.

    Where accounts/OtpService.kt, accounts/OtpRoutes.kt, accounts/SmsPort.kt Proof OtpTest

  4. 04

    Admin session and household lookup

    POST /v1/admin/session mints an 8-hour opaque admin token stored only as SHA-256, rate limited per IP and per email. GET /v1/admin/households?query= resolves a phone, member id or household id through the hopa_admin definer functions and reads the account fields, writing one admin.pii.read line (a hash, never the raw phone or uuid) before any account read. The resolvers now return account_id, folded into the optional db/admin migration after the lane A sync.

    Where admin/AdminSessions.kt, admin/HouseholdLookup.kt, admin/LookupRoutes.kt, db/admin/V5__admin_lookups.sql Proof LookupTest, V2SchemaTest, DiagSendTest

  5. 05

    The console

    A server-rendered console (kotlinx.html) at /console: sign-in, a health page, a household lookup page, a device page and a diag sender. It is cookie-gated, rejects a cross-site Origin on sign-in (login CSRF), caps form bodies at 64 KiB, and renders text nodes only. It never renders a task payload, a conversation or an event.

    Where console/ConsoleRoutes.kt, console/ConsoleViews.kt Proof ConsoleTest

  6. 06

    Android sign-in and the two modes

    A phone-or-password sign-in screen and an AccountViewModel. With a backendUrl configured the app runs against the gateway; with none it stays local-only, and an unreachable gateway degrades to local-only with a banner. The launch decision re-decides when the stored gateway or identity changes.

    Where app/account/SignInScreen.kt, app/account/AccountViewModel.kt, app/navigation/LaunchMode.kt, HopaNavHost.kt Proof SignInViewModelTest, LaunchModeTest, LaunchPairingTest

  7. 07

    Android camera scan and vouch

    CameraX + ML Kit scan the PC’s hopa://pair QR; pasting the string stays as fallback. The confirm screen shows the PC’s fingerprint, refuses a non-pending session, wraps the household content key to the PC with KeyWrap.wrapForDevice and posts the 60-byte blob.

    Where app/pair/ScanScreen.kt, app/pair/VouchViewModel.kt Proof VouchViewModelTest

  8. 08

    Client follow-ups from the lane A review

    The Android link always acks a delivered diag.* on the socket it arrived on. The sidecar refuses a second concurrent backend.pair with ok=false, error="already pairing". The sidecar logs a turn without the goal text — an intentional redaction, not lost output.

    Where app/link/session/BackendSession.kt, apps/windows/sidecar/.../PairingGate.kt, apps/windows/README.md Proof BackendSessionTest, PairingGateTest

How the account fits

The phone is the first and the only required device: it signs up, owns the household content key, and later vouches the PC that scans its QR. The backend meets the two, and it never sees the plaintext key or needs the phone number after login.

  1. The phone signs up.

    POST /v1/accounts carries the E.164 phone, password, platform, name and the device’s public key and self-wrap. One transaction writes the account, the household-of-one, the owner member, the device, the wrap and the tokens.

  2. Signing in mints a device, not history.

    POST /v1/session proves the password and returns a signed-in device with tokens. It cannot read the household key — a new device gets that only by a real wrap from a device that already holds it.

  3. OTP is an alternative credential.

    With HOPA_SMS_ENABLED=true a code can verify a login. A verified login binds and stamps verified_at on an unverified account, so a squatter’s unverified row never blocks the real owner.

  4. The admin looks a household up.

    GET /v1/admin/households?query= reaches tenant rows only through the hopa_admin definer functions. Every read that resolves a phone writes one admin.pii.read line carrying the admin id, the query kind and a truncated hash — never the phone or a uuid.

  5. The PC joins by scanning.

    The PC mints a pending session, the phone scans the QR and vouches the wrapped key, and the PC claims it. That flow is lane A’s verification guide; lane B adds the phone that drives it.

What the admin can and cannot see

The console can read a household’s device inventory and send a diag.ping/state/reset. It cannot read a task payload, a conversation or an event, and it never holds a household key. The phone number is an account column behind the definer functions, not a key, and never appears in the logs.

The console

The console is a plain server-rendered set of pages, so checking it is a browser and two environment values. It needs the admin lookups, which need a superuser database; on a managed Postgres without one the pages that read tenant rows answer 503.

Start it against a database you control

The console reads the household lookup, so run it where HOPA_ADMIN_LOOKUPS=true and the hopa_admin role exists (the local fallback or a self-managed Postgres). Seed one admin with HOPA_ADMIN_EMAIL and HOPA_ADMIN_PASSWORD, or insert a row.

  1. Start the backend

    $env:DATABASE_URL = "postgres://postgres:hopa@127.0.0.1:5432/hopa"
$env:HOPA_ADMIN_EMAIL = "admin@hopa.test"
$env:HOPA_ADMIN_PASSWORD = "a-long-bootstrap-password"
$env:HOPA_ADMIN_LOOKUPS = "true"

apps\android\gradlew.bat -p services\backend run
    Backend start command

    Expected: the migrations apply, the admin seed upserts, and the server prints Responding at http://0.0.0.0:8080.

  2. Sign in and look a household up

    Open http://127.0.0.1:8080/console. It redirects to /console/sign-in; sign in with the seeded email and password. The cookie is HttpOnly, Secure and SameSite=Lax. Then open /console/lookup and query a phone, a member id or a household id.

    Expected: the row shows the household id and the masked phone, and the server logs one admin.pii.read line with a hash — never the phone.

  3. Send a diagnostic

    Open a device page (/console/device/<id>?household=<id>) and send a diag.ping.

    Expected: 202 with a task id and trace; the page shows the audit confirmation; with no socket the task stays queued and delivers on the next hello.

Android: sign in and scan

The app runs in two modes. Point it at a gateway to sign up and sign in; leave the URL blank to stay local-only. The scan flow needs a PC that is already showing its pairing QR. The manual device run is the deferred exit check, not a branch test.

  • Point the app at a gateway. Build with the debug buildConfigField from local.properties, or set the stored backend URL in Settings. A blank URL is the local-only mode.
  • Sign up, then sign in. Sign-up creates the household-of-one and the first device; sign-in on the same account mints a signed-in device. The banner appears when the gateway is unreachable and the app falls back to local-only.
  • Admit a PC. Start the sidecar with --pair-backend <url>, scan its QR (or paste the hopa://pair string), check the fingerprint, and confirm. The phone wraps the key and the PC claims it; the PC’s gateway then opens.

Paste is the fallback, not a lesser path

The camera scan is the user flow, but the paste field ships in the same build. If the camera is unavailable, paste the hopa://pair string; it reaches the same confirm screen and the same vouch.

Troubleshooting

The refusals are deliberately uniform in places. Read the code and the condition before assuming the happy path is broken.

Symptom → cause → fix
Symptom Likely cause Fix
Sign-up or sign-in answers E_AUTH A wrong password, an unknown phone, or a duplicate sign-up race — all deliberately uniform. Check the phone normalizes to E.164 and the password matches. Do not expect a different code; the uniformity is the design (no enumeration).
The admin console answers 401 E_AUTH No admin session, an expired token, or a household device token on /v1/admin/*. Sign in through /v1/admin/session (or the console form). A device token is refused on purpose; the admin resolver only knows admin_sessions.
The lookup route answers 503 E_UNSUPPORTED HOPA_ADMIN_LOOKUPS=false, or the database has no hopa_admin role, so the definer functions were never provisioned. Run on a superuser database with HOPA_ADMIN_LOOKUPS=true. The sign-in route still works; only the tenant reads are gated.
The lookup returns [] The query is well-formed but matches nothing, or the account is tombstoned (deleted_at set). Expected. A tombstoned account renders no phone and accountStatus=none; it is hidden, not an error.
The console sign-in answers 403 The form carried a cross-site Origin (login CSRF). Submit the form from the same host the page was served on. A missing or same-host Origin is allowed.
The console form answers 413 The body is larger than the 64 KiB cap. Trim the field. The console shares the JSON routes’ body cap; an oversized unauthenticated body is refused, not buffered.
OTP routes answer E_UNSUPPORTED HOPA_SMS_ENABLED is not true (it is false by default). Set HOPA_SMS_ENABLED=true to wire the log-only SmsPort. There is no real vendor; the code is logged at INFO, never the phone.
Android stays local-only when a gateway is set The stored backendUrl is blank, or the gateway is unreachable and the app degraded to local-only. Set the backend URL in Settings (or the debug buildConfigField) and check the banner. The launch decision re-decides when the URL or identity changes.
The scan confirm refuses a QR The pending session is expired, already vouched or already claimed; the server reports it as a 200 with a state. Mint a fresh QR on the PC and scan again within five minutes. Only a pending session can be vouched.
The vouch fails with E_SCHEMA The wrap is not exactly 60 bytes, or the session is unknown/expired/claimed. Use KeyWrap.wrapForDevice for this PC key and voucher key; a second vouch is intentionally indistinguishable from an unknown one.
A delivered diag.* is never acked The Android link did not wire onDiagnostic, or the handler threw before the ack. The session acks in a finally, so a throwing handler still acks. Check BackendSessionTest if it regresses.
The sidecar answers a second backend.pair with ok=false A pairing is already in flight. Expected: one concurrent pairing at a time. Wait for the first to finish or fail, then retry.
Backend tests cannot find Docker Testcontainers needs a running engine. Start Docker Desktop. The shared client, app and sidecar suites do not need it.
